What Is LiDAR?

Understanding the core sensing technology behind this project
Introduction

Definition

LiDAR stands for Light Detection and Ranging. It works by emitting laser pulses and measuring the time it takes for each pulse to bounce back from a surface. That travel time is converted into a precise distance measurement — the same principle as sonar, but using light instead of sound.

How a Distance Reading Becomes a 3D Point

  • The sensor fires a laser and measures the round-trip time to the target.
  • Distance (d) is calculated: d = (c × t) / 2
  • An orientation reading (from the IMU) provides a direction vector.
  • Together they place a point in 3D space: (x, y, z)
  • Thousands of these points build a point cloud — a 3D map.

Real-World Uses

  • Self-driving cars
  • Robotics & navigation
  • Architecture & surveying
  • Forestry & geology
  • AR/VR spatial computing
  • Archaeology
This project makes LiDAR technology accessible at low cost using off-the-shelf components and custom software — from a $30 sensor to a live interactive 3D point cloud.

Total Component Cost

All hardware was sourced affordably — TF-Luna (~$30), BNO055 breakout (~$10), Raspberry Pi 5 (~$80), Pi Camera (~$25). The system proves that capable spatial scanning does not require expensive commercial hardware.

Physical Construction

Wiring, CAD design, 3D printing, and final assembly
Construction

Wiring the Scanner

  • TF-Luna → Pi UART: TX→RX (GPIO 14/15), 5 V power & GND
  • BNO055 → Pi I²C: SDA (GPIO 2), SCL (GPIO 3), 3.3 V & GND
  • Pi Camera: CSI ribbon connector to Pi 5 camera port
  • UART and I²C enabled in raspi-config; serial console disabled
  • User added to dialout group for serial port access

CAD & 3D Printing

  • Housing modeled in Rhino 3D (.3dm files)
  • Designed to hold TF-Luna, BNO055, Pi 5, and camera together
  • Sensor alignment baked into the geometry — no re-calibration needed after assembly
  • Printed while software development ran in parallel to save time

Assembly Steps

  • Step 1: Wire TF-Luna to Pi and validate with tfluna_read.py
  • Step 2: Wire BNO055 to Pi and validate with bno055_quat_read.py
  • Step 3: Connect Pi Camera and verify image capture
  • Step 4: Run camera calibration, capture ArUco marker images
  • Step 5: Install components into 3D printed housing
  • Step 6: Re-run all sensor tests as an integrated unit
The housing was designed specifically so the LiDAR sensor, IMU, and camera maintain a fixed spatial relationship. This makes orientation math between sensors consistent and predictable.

Software Architecture

Python tools, HAL interfaces, and the visualization stack
Software

Python Side (Raspberry Pi)

  • HAL (Hardware Abstraction Layer) — clean interfaces that allow any sensor to be swapped or mocked without changing other code
  • tfluna_read.py — UART reader for raw distance frames
  • bno055_quat_read.py — I²C reader for quaternion orientation
  • aruco_pose_demo.py — camera-based marker detection and pose estimation
  • send_sensor_data_udp.py — fuses all sensor streams and broadcasts UDP packets

Testing & Mocking

  • All HAL interfaces have mock implementations for offline testing
  • tests/test_hal.py verifies sensor logic without hardware
  • Mock output logs in test_outputs/ used for data format validation

Visualization Side

  • Unity (C#) — first rendering target, validated the full data pipeline; point cloud shader and UDP receiver
  • Godot 4 (GDScript) — current VR rendering engine; Quest 3 deployment target
  • Custom GLSL point cloud shader for real-time rendering in both engines
  • VR HUD and debug overlay for in-headset diagnostics
The HAL design means the scanner's software can be tested on any computer — not just the Pi — which dramatically speeds up development and debugging cycles.

Data Flow

TF-Luna (UART) ──→ Pi Python tools ──→ Coordinate transform ──→ UDP packet ──→ Unity receiver ──→ Point Cloud render
BNO055 (I²C) ────↗ ArUco Camera ──────────────↗ (scanner origin fusion)

Sending Data with UDP

Bridging the Raspberry Pi scanner to the visualization environment in real time
Networking

Why UDP?

  • Low overhead — no handshaking or connection state
  • Low latency — packets arrive as fast as the network allows
  • Fire-and-forget — acceptable if a few frames are dropped; point clouds are naturally tolerant of gaps
  • Easy to receive — Unity and Python both have simple UDP socket APIs

Packet Contents

  • tfluna — distance (cm), signal strength, temperature
  • bno055 — quaternion orientation (qw, qx, qy, qz)
  • aruco — detected marker IDs and pose vectors (when camera is active)
  • scanner_pose — fused position (from ArUco) + orientation (from IMU)
  • pos_m — final 3D endpoint in world space, ready to plot

Transmission Pipeline

  • Pi reads TF-Luna and BNO055 continuously
  • ArUco detector sends marker poses to local port 6006
  • Aggregator fuses all three streams into one JSON packet
  • Packet broadcast to visualization host on port 5005
  • Unity receiver parses JSON and queues the new point

Frame Mode Tag

Each packet includes a frame mode tag (unity_frame / raw) so the receiving engine knows whether coordinate conversion has already been applied by the Pi — eliminating double-correction bugs.

The Pi owns the coordinate math. The visualization engine just plots what arrives — keeping the rendering side simple and engine-agnostic.

Point Cloud Generation

Turning raw sensor samples into a navigable 3D spatial map
Point Cloud

How Each Point Is Computed

  • 1. Read distance — TF-Luna returns distance d to the nearest surface along the sensor axis.
  • 2. Read orientation — BNO055 returns a unit quaternion q describing where the scanner is pointing in 3D space.
  • 3. Build direction vector — rotate the scanner's forward vector (0, 0, 1) by q to get a world-space direction.
  • 4. Compute endpoint — multiply the direction vector by d to get the absolute 3D position of the detected surface.
  • 5. Accumulate — the new point is appended to the cloud buffer; the render engine draws all accumulated points each frame.

Coordinate System Challenges

  • TF-Luna, BNO055, and Unity each use different axis conventions
  • Iterative live testing was used to determine axis flips, swaps, and yaw offsets
  • Final calibrated settings: Flip Y, Swap Y↔Z, Invert Z, Yaw correction −180°
  • Frame mode tagging prevents double-correction between Pi and engine

Rendering

  • Custom GLSL point cloud shader
  • Points colored by depth or height
  • GPU-side rendering for performance
  • Renders in Unity in real time
ArUco markers improve accuracy by anchoring the scanner's 3D position. Without them, small IMU drift causes scans to "float" over time.

Result

A live, continuously growing 3D point cloud of the environment around the scanner — built in real time as you move the device.

09

Conclusion & Lessons Learned

What was built, what was gained, and where it goes next
Conclusion

What Was Delivered

  • Fully wired handheld LiDAR scanner in a custom 3D printed housing
  • Python sensor stack with HAL interfaces and hardware mock support
  • ArUco camera pipeline for accurate scanner pose estimation
  • UDP sensor fusion stream combining LiDAR, IMU, and camera data
  • Unity point cloud viewer — validated end-to-end pipeline

Key Lessons

  • Test incrementally — isolate components first, integrate second
  • Pivot strategically — when a camera driver blocked progress, shifting focus to Unity visualization kept the project moving forward
  • Coordinate systems matter — every engine and sensor has its own axis; mapping them correctly is non-trivial
  • Sensor fusion > single-source — combining IMU + ArUco produces far more stable results than either alone

Skills Developed

  • Embedded hardware integration (UART, I²C, GPIO)
  • Computer vision (camera calibration, ArUco detection)
  • 3D math: quaternions, coordinate transforms, point clouds
  • Network programming (UDP socket design)
  • Game engine development (Unity C#)
  • CAD design and 3D printing
This project combined hardware, software, networking, computer vision, and 3D math into a single working pipeline — demonstrating what a computer science education looks like in practice.

Future Directions

  • SLAM — simultaneous localization and mapping during movement
  • Point cloud export and mesh reconstruction
  • Smoothed sensor fusion with complementary or Kalman filtering
